# UC130／UC131：分配衝突與失效人選恢復

本輪從184列矩陣中選出仍為local NOT_RUN的UC130及UC131。這是原100 UC的補驗，不新增或改名原F／R／UC／LA。只驗本機component、in-process server handler及新隔離SQL；沒有原生Auth、HTTP、RLS/app-role或browser reload接受。

## 原問題與最小修補

UC130要求同一version下，甲成功指派後，乙的舊提交得到衝突並重讀，不覆蓋甲。主線既有case/work鎖及version比較已保護寫入；本輪沒有重寫這套鎖。實際SQL先證明winner、stale loser、重送、審計與後續新version提交均正確，但兩個版本拒絕只拋一般Error，缺少可辨識409契約。

UC131要求已選人選被停用後，server拒絕舊選擇、保留其他輸入並提示重選。既有users／staff_profiles share lock及推薦政策已拒絕停用人選；一般Error無法區分「確認不合資格」和「DB讀取失敗」。新增StaffStateUnavailableError只標示已成功讀取但沒有合資格row的情形；未知DB錯誤仍原樣拋出。Work assignment將已知人選失效轉409，actor失效轉403，未改其他使用者的權限或驗證政策。

畫面原本永久使用開dialog時的item.version、只顯示一般錯誤、沒有重讀入口，亦沒有確認儲存的selected人選仍存在於當前可用名單。修補保留已檢視snapshot，任何mutation error（包括未知結果）均鎖住重試，直到使用者明確重讀隊列及人選兩者成功；保留角色及例外理由，清除舊選擇，再由使用者重新選擇及確認新version。沒有自動重送。
