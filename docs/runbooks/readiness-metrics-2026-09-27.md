## Reproduced failures

- A case with all checklist rows marked Verified but payment pending appeared in `readyToFile` (RED work-view test: one false ready row).
- Under one company scope, the board counted a Filed overdue case but the dashboard excluded it (RED disposable-Postgres test: board 2, expected 1).
- The dashboard called a count of outstanding checklist items “Missing documents”, while the board counted cases. A failed or pending board totals query rendered zeros.

## Local implementation

`evaluateCaseReadiness` consumes a consistent snapshot with evidence and payment states, existing `ManifestResult`, the current canonical-manifest hash, human approval, verified submission, reconciled return, and existing completion blockers. Unknown or superseded evidence blocks package approval. A changed manifest invalidates approval. Recording submission is available only before a submission exists; completion needs a verified submission and matched return. The evaluator makes no permission decision; each mutation must reload and re-evaluate the version inside its server transaction.

T14 now persists package approval, and the single-case manual-submission gate below checks its current bytes. The “可以交件” work view remains explicitly unreleased until it has a complete indexed, authorized snapshot reader; checklist completion alone cannot release it. Its interface accepts a complete map of server-evaluated readiness results, and an incomplete map cannot release the view.

Board and dashboard now share one authorized SQL aggregate and date, exclude Filed/Completed from active work, and split missing-evidence **cases** from missing-evidence **items**. Payment lacking a proof-document link remains pending. The board does not show zero tiles while the cases/totals queries are pending or failed; a failed totals read offers retry. The dashboard label names cases, not items. The high-risk board tile remains explicitly limited to loaded rows; a firm-wide risk aggregate requires a separately validated domain projection.

## T03 manual-submission readiness gate — 2026-09-28

A named integration RED showed that the case detail could offer “record external submission” for an approved package whose current bytes or manifest could not be verified. The case detail now asks an actor-scoped GET reader for a per-case submission decision. The reader uses one repeatable-read, read-only database snapshot to check current staff identity, case visibility, the current role's `record_submission` permission, open case status, latest approved package and absence of an active handoff. It then reuses the approved-download path to check the current manifest, payment allocation and proof, document versions and scan states, and stored ZIP bytes. Missing/draft/closed/previously handed-off cases are blocked; failed verification is `unknown` and blocks the action. A retry is available for an unknown/error read. The POST still reloads and validates independently in its own transaction, so the GET is only a user-facing preview.

The integration test covered a forged auth identity, no package, draft package, approved/current package, permission revocation, changed requirement manifest and deleted ZIP. A separate test exercised the real read-only transaction path rather than an injected write-capable fixture; the first implementation's `FOR UPDATE` permission helper would have failed there, so the reader now uses the same pure permission rule with current `users` and case rows. The interaction RED/GREEN test covers the disabled submission button for unverifiable bytes, with a positive approved-package control. Focused DB/UI checks passed 2 files / 18 tests before the added read-only and revocation assertions; DB checks with those assertions passed 11/11. The final disposable-PostgreSQL full suite passed 226 files with 1 skipped, 1934 tests with 5 skipped; typecheck and Vercel preset build passed; lint reported 0 errors and the inherited work-queue warning. No schema or production data changed.

This is a **single-case** submission preview, not the complete `CaseReadinessSnapshot` reader or an indexed firm-wide `readyToFile` queue. The queue remains explicitly unreleased; a blank queue is not evidence of zero ready cases. T03 stays in progress pending that indexed reader, authenticated runtime/browser verification and the production binding/ledger gate.

## T03 payment-proof stored-byte correction — 2026-09-29

A RED disposable-PostgreSQL and in-memory-storage test approved a current package, deleted the reconciled payment proof object, and still received `ready` from the submission GET. The package snapshot had checked matching database checksums, provider scan and human review, but had not re-read the payment proof bytes. This could also affect prepare/approve and the new ready queue.

The central package snapshot now requires the proof version's object key and content type, reads the object, checks stored metadata and size, and computes SHA-256 over its actual bytes. It reuses the same source-byte verifier used by the filing document ZIP builder. Every existing package snapshot call passes storage, so prepare, approve, approved download and readiness share this gate. A missing object and a replacement object that advertised the original checksum/size/type but contained different bytes both return `unknown/package-unverifiable` from the GET. The write paths fail before a new package can be approved. No automatic retry or provider mutation is involved.

The named test failed before implementation with `ready`, then passed after the fix. The affected package/submission integration file passed 15/15; package artifact byte-integrity unit test passed 1/1. The complete disposable PostgreSQL project passed 35 files/326 tests with 1 file/5 tests skipped; typecheck passed. Production DB, storage and deployment were not touched.

## T03 C2 case snapshot reader — 2026-09-29

An actor-scoped GET now assembles the package-workflow `CaseReadinessSnapshot` in one repeatable-read, read-only database transaction. It reuses the package service's document manifest and payment proof checks, recomputes current source bytes, and uses the approved-download inspector for the latest approved ZIP. Recorded manual submission and accepted, named human return reconciliation are checked against current proof bytes. An active handoff, missing object, changed ZIP, stale document, pending return or revoked actor cannot produce a ready action preview. The case page shows these evidence conditions as a read-only preview; each mutation retains its independent server validation. The snapshot `revision` is the package revision, not a whole-case CAS.
