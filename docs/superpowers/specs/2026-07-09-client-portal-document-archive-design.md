# Client Portal And Document Archive Design

## Summary

This phase extends the annual return workflow outside the staff-only cockpit. It adds a mocked client action portal and turns the existing `/documents` stub into an internal document archive.

The portal gives clients a clear view of what Kossilon needs from them: missing documents, payment acknowledgement, signature status, packet approval, and filing receipt visibility. Portal actions remain mocked and local-state only, but they update the internal archive and annual return timeline so staff can see the same activity from the case record.

## Goals

- Add a mocked client-facing annual return action portal.
- Let clients mock-upload and replace required documents.
- Let clients acknowledge payment instructions and approve a filing packet.
- Show sent reminders, client actions, packet status, and receipt history in the portal.
- Replace `/documents` with a staff-facing archive tied to annual return cases.
- Keep portal actions, archive rows, and annual return timelines synchronized through local state.
- Preserve the existing mocked architecture: no real auth, uploads, payments, signatures, backend, or external APIs.

## Non-Goals

- No real client authentication or portal login.
- No real file upload, storage, virus scanning, or document preview.
- No real payment collection or e-signature integration.
- No real Companies Registry submission.
- No role or permission overhaul.
- No broad redesign of annual return, WhatsApp, payments, or tasks.

## Recommended Direction

Use a **Client Action Portal + Document Archive** approach.

The portal gives the demo an outside-in client journey, while the document archive makes the same activity credible for staff. Both surfaces should read from one local document/action model so a mock upload in the portal immediately appears in the archive and on the annual return case timeline.

Alternative approaches considered:

- **Archive-first:** Build `/documents` as the source of truth before adding portal actions. This is clean internally, but less compelling because the client journey stays secondary.
- **Portal-first:** Build only the client portal and leave `/documents` lightweight. This is faster, but misses the staff-facing audit trail that makes the workflow feel production-real.

The combined approach best fits the current branch because the previous phases already built packet readiness, follow-up sends, submissions, receipts, and case timelines.

## Architecture

Add a focused local document/action store:

`src/lib/client-portal-store.ts`

The store should use the same `useSyncExternalStore` pattern used by the annual return and knowledge base stores.

The annual return store remains the source of truth for case readiness, packet state, follow-up sends, submissions, and receipts. The portal store owns mocked client documents and client-facing actions, then references annual return cases by id.

The portal store should expose:

- Document records.
- Client action records.
- Portal activity records.
- Archive row derivation.
- Required client action derivation.
- Portal progress derivation.
- Mutations for upload, replace, acknowledge payment, and approve packet.

The annual return store should expose one small integration helper for portal-originated timeline entries:

- `appendClientPortalTimelineEvent(caseId, event)`

This helper should append an audit-style timeline event without changing readiness, packet, or filing status. The key boundary is that the portal store should not duplicate annual return readiness, packet, or filing logic.

## Data Model

### Client Documents

Each document record should include:

- Stable id.
- Annual return case id.
- Requirement id when linked to a required document.
- Company/client metadata needed for archive filtering.
- Title.
- Filename.
- Category: identity, registry, signature, payment, packet, submission, receipt, other.
- Source: client portal, staff packet builder, filing submission, filing receipt.
- Status: required, uploaded, superseded, accepted, rejected, generated.
- Uploaded or generated by.
- Uploaded or generated timestamp.
- Superseded document id when replacement occurs.

Only the latest non-superseded upload for a requirement should satisfy that requirement. Superseded files remain visible in `/documents`.

### Client Actions

Each client action should include:

- Stable id.
- Annual return case id.
- Type: upload document, replace document, acknowledge payment, approve packet, view receipt.
- Actor name.
- Timestamp.
- Status: completed or blocked.
- Human-readable summary.

These actions feed the portal activity list and the annual return case timeline.

### Archive Rows

Archive rows should be derived from:

- Client-uploaded documents.
- Superseded client documents.
- Packet artifacts from annual return packet state.
- Filing submission references.
- Filing receipt records.

This allows `/documents` to represent the whole document history without introducing a separate backend-like persistence layer.

## Routes And UI

### `/portal`

Use a single `/portal` route. It should default to the first active annual return case and provide a case selector for seeded clients. When opened with a `caseId` search parameter, it should select that case if it exists.

The page should feel like an action checklist, not a marketing page.

Top area:

- Company name.
- Annual return due date.
- Filing and packet status.
- Next client action.
- Progress strip for documents, payment, signature, packet approval, and receipt.

Main actions:

- Required documents list with mock Upload and Replace actions.
- Packet review section with packet requirement summary and Approve packet action.
- Payment/signature acknowledgement panel.
- Activity feed showing reminders sent, uploads made, packet approved, receipt accepted, and receipt viewed.

Controls should become read-only once the case is filed or the packet receipt is accepted. The portal should still show the complete archive and receipt history.

### `/documents`

Replace the current stub with a dense staff archive.

Archive controls:

- Search by company, contact, title, or filename.
- Filter by source.
- Filter by category.
- Filter by status.
- Filter by case.

The route should accept an optional `caseId` search parameter so staff links can open the archive scoped to a case.

Archive rows:

- Document title and filename.
- Company.
- Category.
- Source.
- Status.
- Timestamp.
- Uploaded or generated by.
- Linked annual return case.

Rows for generated packet artifacts, filing submissions, and receipts should be read-only. Client-uploaded rows should show whether they are current or superseded.

### `/annual-returns/$id`

Add a compact Client Portal Activity panel:

- Latest upload or client action.
- Outstanding client action count.
- Archive document count.
- Latest portal action timestamp.
- Link to open the portal mock for the case.
- Link to `/documents` with the case id search parameter applied.

Do not let this panel crowd out the existing blockers, packet builder, follow-ups, or timeline. It should support the operator workflow, not become the main detail page.

## Workflow Behavior

### Upload Document

When a client mock-uploads a required document:

- Create a document record.
- Mark it as the current uploaded document for the requirement.
- Append a client action record.
- Append an annual return timeline event.
- Update portal progress and required actions.
- Make the document appear in `/documents`.

If the upload satisfies an annual return document requirement, the implementation may call the existing annual return document mutation. If the requirement mapping is not exact, keep the portal upload as archive/activity state and make the remaining blocker visible.

### Replace Document

When a client replaces a document:

- Mark the previous current document as superseded.
- Create a new uploaded document record.
- Preserve both rows in `/documents`.
- Append a timeline event explaining the replacement.
- Keep only the new document satisfying the requirement.

### Acknowledge Payment

Payment acknowledgement should not mark the annual return payment as paid by itself. It should record that the client saw or acknowledged payment instructions. The staff-side payment status remains controlled by existing annual return payment mutations.

### Approve Packet

Packet approval should be allowed only when portal-visible required documents are present and the annual return packet is not filed or accepted.

Approving the packet should:

- Create a client action.
- Append a timeline event.
- Update portal progress.
- Surface the approval in `/documents` as a generated packet approval artifact or in the activity feed.

It should not submit the filing packet. Staff submission remains in the annual return case workflow.

### View Receipt

When a receipt exists, the portal should show it as read-only. A mock "View receipt" action may append portal activity, but it should not change the filing state.

## Error Handling And Guardrails

- Unknown portal case ids should render a not-found state with a link back to the staff app.
- Filed or receipt-accepted cases should render upload, payment acknowledgement, and packet approval controls as read-only.
- Packet approval should list missing portal-visible requirements when blocked.
- Superseded documents should remain visible but clearly stop satisfying requirements.
- Generated submission and receipt rows should be read-only.
- Portal mutations should be safe if the linked annual return case no longer exists.
- The document archive should handle an empty result set for filters.

## Testing And Verification

Pure helper tests should cover:

- Archive row derivation from uploads, superseded documents, packet artifacts, submissions, and receipts.
- Required portal action derivation for missing documents, payment acknowledgement, packet approval, and receipt visibility.
- Portal progress calculation.
- Current-document selection when documents are replaced.
- Packet approval guardrails.
- Filed/accepted cases disabling client actions.

Route and interaction tests should cover:

- `/portal` renders the selected case status and next client action.
- Uploading a document updates portal progress and `/documents`.
- Replacing a document keeps the old row as superseded.
- Approving a packet appends activity and timeline state.
- `/documents` filters by source, category, status, and search text.
- `/annual-returns/$id` shows portal activity, archive count, and portal link.

Manual verification should cover:

- Open portal for each seeded annual return case.
- Upload each required document type and confirm progress updates.
- Replace a document and confirm the archive shows both current and superseded rows.
- Attempt packet approval while requirements are missing and confirm the guardrail.
- Complete required portal actions and confirm annual return detail timeline reflects them.
- Submit and accept a filing receipt from staff workflow, then confirm portal receipt visibility and archive receipt rows.
- Filter `/documents` across client upload, packet, submission, and receipt sources.

Automated verification should run the annual return store tests, new portal/document store tests, route tests, type checks, lint, and build if the local toolchain is available.

## Implementation Boundaries

Expected file changes:

- New `src/lib/client-portal-store.ts`.
- New `src/lib/client-portal-store.test.ts`.
- New route `src/routes/portal.tsx`.
- Replace `src/routes/documents.tsx`.
- Update `src/routes/annual-returns.$id.tsx`.
- Update `src/components/app-sidebar.tsx` to include the portal demo route.
- Update route tests for portal, documents, and annual return detail.

Avoid introducing real upload APIs, server routes, auth checks, or a standalone backend-like document service. Keep the state local, deterministic, and easy to test.
